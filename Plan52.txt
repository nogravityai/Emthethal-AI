CORE ARCHITECTURAL PRINCIPLE

This system processes documents as ISOLATED SINGLE-PAGE UNITS.

Each page is treated as an independent compilation target with its own:
Coordinate system
Semantic zones
Field graph
Evidence ledger
HITL operations

Multi-page documents are handled at the ORCHESTRATION layer by processing
each page independently and aggregating results externally via OrchestrationContract.

This architecture eliminates:
Cross-page zone spanning
Page-to-page dependency chains
Multi-page transaction complexity
Page index propagation bugs
Concurrent page modification conflicts

This system is NOT an OCR platform.
It is a Visual-to-Structured Semantic Compiler.
The page becomes a semantic graph. This distinction is architectural, not aesthetic.

================================================================================
CRITICAL ARCHITECTURAL RULES (NON-NEGOTIABLE)

RULE 1: SINGLE-PAGE ATOMIC BOUNDARY
Every processing unit represents EXACTLY ONE PAGE.
All coordinates are in pixels relative to page bounds [0,0] → [page_width, page_height].
All zones exist within a single page boundary.
All evidence references a single page context.
Page context is established once at pipeline entry and never changes.

RULE 2: THREE-STAGE PIPELINE INTEGRITY (NO STAGE EXPLOSION)
The orchestrator MUST remain strictly:
PerceptionStage → ReasoningStage → OperationalStage
Do NOT create new top-level pipeline stages.
Add internal engines, compilers, and graph builders INSIDE existing stages.

RULE 3: GOLDEN RULES OF EVIDENCE IMMUTABILITY
Perception produces IMMUTABLE evidence only.
Reasoning NEVER modifies OCR coordinates or raw geometry.
Operational NEVER performs destructive mutations.
All edits are append-only ledger operations.

RULE 4: ZONE COLLISION RESOLUTION PROTOCOL (DETERMINISTIC)
When primitives fall within overlapping zones, assignment follows this exact priority:
Priority 1: STRICT_CONTAINMENT — fully contained in exactly ONE zone → assign to that zone.
Priority 2: DEEPEST_TREE_LEVEL — assign to zone with deepest parent_zone_id chain length.
Priority 3: SMALLEST_AREA_ZONE — if tree depth equal, assign to smallest bbox area.
Priority 4: HIGHEST_OVERLAP_RATIO — (intersection_area / primitive_area); assign to highest.
Priority 5: LEXICAL_TIE_BREAKER — sort zone_id alphabetically; assign to first.
This algorithm MUST be deterministic and produce identical results on replay.

RULE 5: LAYOUTLMV3 IS ASSISTIVE ONLY (NOT AUTHORITATIVE)
LayoutLMv3 MUST NOT: control extraction logic, determine final field values,
mutate geometry, or override deterministic rules.
LayoutLMv3 MAY ONLY: suggest zone labels, suggest semantic field names,
classify section types, assist in template matching, and generate semantic hints
with confidence scores strictly below 1.0.
Geometry-first deterministic logic remains PRIMARY and AUTHORITATIVE.

RULE 6: DETECTION-FIRST, TEMPLATE-ASSISTED (ANTI-OVERFITTING)
Templates are acceleration tools, NOT primary detection mechanisms.
The system MUST always run Detection-first on every page regardless of template availability.
Template matches are confidence-weighted proposals only.
Merge template projections with detected zones using the hybrid approach.
NEVER rely solely on template alignment as the extraction source.

RULE 7: UNIFIED RUNTIME STATE CONTRACT
All engines operate on and mutate ONE shared state object: PageCompilationState.
No engine is allowed to maintain private state not reflected in this object.
This prevents circular dependencies, duplicated caches, and hidden mutations.

RULE 8: ZERO TOLERANCE FOR HACKS
FORBIDDEN at all times:
if form_type == "x": ... — use rule-based engines instead.
Special-case branches — encode as explicit rules with confidence scores.
Hardcoded field name strings — use schema registry and aliases.
Silent workarounds — all edge cases enter through a named engine.
Missing provenance — every extracted value MUST carry a Provenance record.
Any new logic MUST enter through a named engine, a named rule, a confidence score,
and provenance tracking. No exceptions.

RULE 9: DETERMINISTIC PARALLEL REDUCTION
All engines that process in parallel MUST apply a deterministic merge strategy
before writing to PageCompilationState:
Sort all partial results by their primary identifier (zone_id, primitive_id,
row_index, etc.) in ascending lexical or numeric order before merging.
This guarantees state_hash verification passes on every replay regardless of
thread scheduling order.

RULE 10: ATOMIC SEQUENCE LOCKING FOR LEDGER
Every ledger write operation carries a strictly monotonic ledger_sequence_number.
The SnapshotCompilerEngine MUST reject any snapshot write if the incoming
sequence number ≤ the sequence number of the currently stored snapshot.
After each successful LedgerOperationEngine commit, state_hash is recomputed.
A mismatch with the expected hash triggers DeterminismViolationAlert immediately
(no waiting for replay).

class BoundingBox(BaseModel):
"""Axis-aligned bounding box. All coordinates in pixels relative to single page bounds."""
x_min: int = Field(..., ge=0)
y_min: int = Field(..., ge=0)
x_max: int = Field(..., gt=0)
y_max: int = Field(..., gt=0)

@validator('x_max')
def validate_x(cls, v, values):
if 'x_min' in values and v <= values['x_min']:
raise ValueError('x_max must be greater than x_min')
return v

@validator('y_max')
def validate_y(cls, v, values):
if 'y_min' in values and v <= values['y_min']:
raise ValueError('y_max must be greater than y_min')
return v

def area(self) -> int:
return (self.x_max - self.x_min) * (self.y_max - self.y_min)

def contains(self, other: 'BoundingBox') -> bool:
return (self.x_min <= other.x_min and self.x_max >= other.x_max and
self.y_min <= other.y_min and self.y_max >= other.y_max)

def intersection_area(self, other: 'BoundingBox') -> int:
x_overlap = max(0, min(self.x_max, other.x_max) - max(self.x_min, other.x_min))
y_overlap = max(0, min(self.y_max, other.y_max) - max(self.y_min, other.y_min))
return x_overlap * y_overlap

def iou(self, other: 'BoundingBox') -> float:
inter = self.intersection_area(other)
union = self.area() + other.area() - inter
return inter / union if union > 0 else 0.0

class AffineMatrix(BaseModel):
"""2D affine transformation for deskewing and template alignment."""
a: float; b: float; c: float; d: float; tx: float; ty: float

def transform_point(self, x: float, y: float) -> tuple:
return (self.a * x + self.b * y + self.tx,
self.c * x + self.d * y + self.ty)

LARGE CONTAINER PARTITIONING — EXTENDED TO RepeatedFieldPattern [CLOSES Gap#16]

LargeContainerPartitioningStrategy is activated when EITHER:
(a) InferredGrid.row_count > 50, OR
(b) RepeatedFieldPattern.instances count > 50

For RepeatedFieldPattern:
Split instances into overlapping windows of 20 instances each with 2-instance overlap.
Process each window independently in CompositeFieldContainerEngine.
Merge results by deduplicating on instance_index.

Rationale: RepeatedFieldPattern instances undergo the same O(n²) field-linking
complexity as grid rows and must be subject to the same protection threshold.

CONSTRAINT REGISTRY — FORMAT AND HOT-RELOAD [CLOSES Gap#28]

FORMAT: Versioned JSON file.
SCHEMA:
{
"graph_version": "1.2",
"namespace": "healthcare.patient",
"constraints": [ ...CrossFieldConstraint objects... ]
}

LOCATION: config/constraints/{namespace}.json (one file per namespace).

HOT-RELOAD PROTOCOL:
1. FileWatcher monitors config/constraints/ for changes.
2. On change: validate new file against ConstraintGraph schema.
3. If valid: swap ConstraintGraph in-memory for SemanticValidationEngine.
Pages currently being processed COMPLETE with the old ConstraintGraph.
New pages use the new ConstraintGraph.
4. If invalid: reject silently; log error; keep old ConstraintGraph active.
5. Log all hot-reload events with timestamp and graph_version.

================================================================================
CONCURRENT HITL OPERATIONS — OPTIMISTIC LOCKING [CLOSES Gap#26, Gap#27]

OPTIMISTIC LOCK PROTOCOL (closes Gap#26):
1. Operator fetches current ledger_sequence_number (N) at session open.
2. All operations include expected_sequence = N.
3. LedgerOperationEngine checks: incoming.expected_sequence == current_max_sequence.
If match: accept, increment, commit.
If mismatch: reject with ConcurrentModificationError(expected=N, actual=current).
4. Client receives ConcurrentModificationError and must refresh state before retrying.

STATE REFRESH PROTOCOL (closes Gap#27):
Service publishes PageMutationEvent (page_id, new_sequence_number) to an
internal event bus (e.g. Redis pub/sub or in-process EventEmitter) after
each successful LedgerOperationEngine commit.
All active HITL sessions subscribed to that page_id receive the event and
must call StateRefresh(page_id) to reload the latest snapshot + delta operations.
Sessions that ignore StateRefresh events and attempt to commit will receive
ConcurrentModificationError per the optimistic lock protocol above.

================================================================================
PAGE IMAGE LIFECYCLE [CLOSES Gap#29]

page_image is NOT stored in PageCompilationState.

LIFECYCLE:
1. Loaded as a read-only ndarray by OCRAdapterEngine at pipeline entry.
2. Passed to PrimitiveShapeDetectorEngine and SemanticZoneProposalEngine
as a read-only reference (no copy). Python's GIL protects read-only
ndarray access; no per-thread copy is needed for parallel reads.
3. Explicitly released (del page_image; gc.collect()) after PerceptionStage
completes and before ReasoningStage begins.
4. For template matching (Phase 5), the page_image is reloaded from the
PageImageStore using page_id if needed. It is released immediately after
ORB feature extraction.

Memory budget per page: peak ~50MB for a 300 DPI A4 page (RGB ndarray).
If multiple pages are processed in parallel, process pool must cap concurrent
page_image loads to (available_memory_gb × 1000) / 50 pages.

================================================================================
SCHEMA REGISTRY STORAGE [CLOSES Gap#30]

STORAGE: Two-tier.
Tier 1 (authoritative): Versioned JSON file at config/schema/{namespace}.v{N}.json
Tier 2 (cache): Database table canonical_schema with columns:
(namespace, schema_version, canonical_tag, aliases, validation_rules, deprecated_tags, is_active)

MANAGEMENT:
• New versions are added by creating a new JSON file and running SchemaRegistryLoader.
• SchemaRegistryLoader validates the file, inserts/updates the database cache, and
marks the new version as active. Old versions remain (deprecated_in_version set).
• Deployments across environments: JSON files are version-controlled in the repository.
The database cache is rebuilt from JSON files on first startup in each environment.

DATA STORE MIGRATION [CLOSES Gap#31]

DataStoreMigrationRunner is a CLI tool (scripts/migrate.py) that:
1. Reads the current data schema version from each store metadata table.
2. Applies pending migration scripts in order (migration_{from}_{to}.py).
3. Records the new schema version in the store metadata table.

Applies to:
• HITL Learning Store (field correction history)
• Template Registry (FormTemplate blobs and RelativePosition data)
• ConstraintRegistry (CrossFieldConstraint data)
• SnapshotStore (CompiledSnapshot blobs)

Migration scripts are idempotent: running twice produces the same result as running once.
Each migration script is tested against a snapshot of production data before deployment.

KNOWN LIMITATIONS (documented, not bugs)

KL-1 (Gap#18): max_y_tolerance is computed once per zone from median_line_height.
If a zone contains mixed font sizes, tolerance may be imprecise for outlier lines.
Mitigation: zone segmentation in SemanticZoneProposalEngine typically separates
regions with very different font sizes into distinct zones.
Target fix: v5.3 — per-line dynamic tolerance.

KL-2 (Gap#35): Deskew applies a single Affine Transform per page (uniform skew assumption).
Pages with non-uniform warping (physical fold, roller damage) may have residual distortion
after deskew in the affected region.
Mitigation: ReasoningStage geometric tolerance parameters (e.g. max_y_tolerance,
snap_radius) absorb minor residual distortion.
Target fix: v5.3 — per-region deskew using piecewise affine transform.
